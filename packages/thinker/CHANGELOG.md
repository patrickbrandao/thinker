# thinker

## 0.1.2

### Patch Changes

- 7aeb4e9: Virtual models, part 1 (ADR 0004): new `virtual_models` table and admin API at `/api/v1/routing/:agentName/virtual-models` to create, edit, enable, reorder and delete per-harness model names with a primary, up to 5 fallbacks and "continue on Default". Routes are validated strictly when saved, and the listing shows which real model ids each name shadows and its context window. The proxy does not use them yet.
- 257ebc4: Virtual models, part 2 (ADR 0004): the proxy now accepts a virtual model name in `model` on `/v1/chat/completions`, `/v1/responses` and `/v1/messages`. An enabled virtual model comes first, ahead of header tiers, and routes through its own chain, then through the Default tier's chain when "continue on Default" is on, with runtime fallback. A chain with no available route answers the new error M301. Responses carry `X-Thinker-Reason: virtual-model` and `X-Thinker-Virtual-Model`, message log rows record the virtual model, and per-model parameters apply per route (`virtual:<id>` for its own routes, `tier:default` for the borrowed ones). Header tiers, `auto`, heartbeats and `POST /api/v1/routing/resolve` keep their behavior.
- 5ed7392: Virtual models, part 3 (ADR 0004): `GET /v1/models` now lists `auto`, then the key's agent's enabled virtual models (in their configured order), then the real models. A real model whose id matches a virtual model's name, ignoring case, is hidden while that virtual model is enabled. `auto` and virtual models publish `context_length`, the smallest context window among the routes that can serve them, and omit it when any of those windows is unknown. They never carry `capabilities`, `cost` or route metadata.
- 7f4a90c: Virtual models, part 4 (ADR 0004): the harness Routing page has a "Virtual models" section, separate from the custom tiers. Each card shows the name, the primary model and up to 5 fallbacks, and switches for active, "Continue on Default" and stream mode, plus a warning when the name shadows a real model id. The create/edit modal checks the name live with the backend's rule and shows backend errors next to the field or the model they concern. Cards reorder by drag (or the arrow keys on the handle), and each one has a copyable example with the harness's base URL and `model: "<name>"`. The message log and the message details show the virtual model a request used. Harness setup screens list the active virtual models as values of `model` next to `auto`, and the SDK snippets can switch to one.
- fd8e7ad: Virtual models, part 5 (ADR 0004): virtual models in the MCP server and the `thinker` CLI. New MCP tools `thinker_routing_virtual_list`, `_create`, `_update` and `_delete`, and CLI commands `thinker routing virtual list|create|update|delete|enable|disable` (`--model`, repeatable `--fallback`, `--continue-on-default`; `delete` needs `--yes`). `thinker_routing_status` and `thinker routing status` list the virtual models, and `thinker_routing_test` / `thinker routing test --model <virtual>` report the virtual model and routing reason the request went through. Model params can be addressed by virtual model with the `virtual` field of `thinker_routing_params_get`/`_set` and `--virtual` on `thinker routing params get|set`, both exclusive with the tier selector, through the new `GET|PATCH /api/v1/routing/:agent/virtual-model-params?virtual=<name>` endpoint (scope `virtual:<id>`). The CLI agent skill documents them. `thinker_routing_status` keeps its `enabled`/`reason` verdict for `model: "auto"` (now labeled `status_for: "auto"`) and adds `routes_by_virtual_model` and `active_virtual_models`; when only virtual models can route, `reason` is `auto_not_routable` and `auto_reason` keeps the auto-route cause. `thinker routing status` adds the same two fields. Contract change: in the params view returned by `thinker_routing_params_get`/`_set` and the tier/virtual params endpoints, `tier` is now optional (present when the target is a tier) and `virtual` is set when the target is a virtual model. The params `model` selector (tiers and virtual models, MCP, CLI and REST) now also accepts a route's public id, as `/v1/models` lists it (`<alias>/<model>` for a custom provider), and its bare native id when only one connection of the chain has it, matched in layers (stored id, then public id, then native names) so an id that names one route exactly is never made ambiguous; the view adds `public_model` and `public_models`. The virtual model listing adds `routable`, computed on the chain the proxy builds (its own routes, then only the `default` slot with continue on Default), which both status readbacks use.
- 0db72d8: Virtual models, part 7 (ADR 0004): PT-BR documentation for virtual models (routing page, harness connection, CLI), the `X-Thinker-*` response headers and the `M301` error entry.
- 7cdc53c: Fix (#197): a virtual model whose routes all belong to a provider the agent no longer has (disconnected, or disabled for the agent) is no longer reported as routable. The virtual model listing (`routable`), `thinker routing status` and `thinker_routing_status` (`routes_by_virtual_model`, `active_virtual_models`) now judge a route with no discovered models the way the proxy does: it counts only when the agent has an active, usable record for its provider. A connected provider whose discovery has no models yet still counts, with an unknown window. The same rule applies to `context_length` (virtual model listing and `GET /v1/models`, virtual models and `auto`): a route of a removed provider no longer enters the calculation, so the published window is the smallest among the routes that can actually serve the request (ADR 0004, section 7).
- 3ebc3a7: Disconnecting, disabling for a harness or removing (custom provider) a provider that a virtual model routes to is now refused with 409, as it already was for tiers. Any override or fallback of a virtual model counts, enabled or disabled; routes inherited through Continue on Default do not, since the `default` tier guard already covers them. The 409 message names the virtual model (`agent "…", virtual model "…", primary: …`). The disable-impact endpoint (`GET /api/v1/agents/:agent/enabled-providers/:id/impact`) gains `affected_virtual_models` (id, name, agent, model, position) next to `affected_tiers`, the MCP `thinker_agent_provider_disable` tool applies the same guard, and the dashboard names the virtual models when it blocks a disable (ADR 0004, #176). Renaming a provider key now also rewrites the key pins of virtual models in the tenant (override and fallbacks), and deleting an inactive key clears them, as it already did for tiers and header tiers, so a pinned virtual model no longer falls back to the provider's first key.

## 0.1.1

### Patch Changes

- New `THINKER_SETUP_TOKEN` env var: the operator can choose the first-setup token (16+ characters) and hand it over without reading the server log. It is never logged. Without it, a random one-time token is still printed to the log. Release notes in Portuguese: [`docs/releases/0.1.1.md`](../../docs/releases/0.1.1.md).
